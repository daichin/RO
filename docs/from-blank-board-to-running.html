韌體上線 · 燒錄與部署

從空板到運轉

板子已經確認能燒錄了。接下來把 NodeMCU 韌體燒進板子、把這個工作區的 Lua 沖洗邏輯打包成 LFS 映像送上去，最後讓它真正開始運轉。

ESP8266 · NodeMCU 韌體 + Lua 應用 esptool 燒錄 LFS 128 KB integer build
✓
前置條件：板子已通過燒錄前的硬體檢查（esptool.py chip_id 讀得到 Chip ID）。還沒做過的話先看 docs/can-this-board-be-flashed.html，確認板子能通電、序列埠認得到、esptool 連得上，再回來繼續。

先弄懂三層

init.lua（SPIFFS）

開機入口。放開繼電器、掛 LFS loader、啟動狀態機。唯一不能編譯、不能進 LFS 的檔案

序列埠逐行上傳

lfs.img（Lua Flash Store）

cfg · log · ro · web · wifi_cfg 的位元組碼，住在 flash 而不是 RAM

luac.cross.int 打包

NodeMCU 韌體（Lua 直譯器）

跑在 ESP8266 上的 C 韌體本體，提供 gpio／tmr／file／net／wifi 等模組

esptool 燒錄

最下層只燒一次；改沖洗邏輯時重打包中間層；init.lua 幾乎不用動。LFS 不是選配 —— ESP8266 開機只有約 41 KB 堆積，五個模組全載進 RAM 要 39.4 KB，網頁介面根本起不來。理由與實測數字見 firmware/README.md。

建置與上線流程

八個步驟，由下層往上層推進。

1

編一份帶 LFS 的韌體

到 nodemcu-build.com，勾這五個模組（string table math 是 Lua 核心，不用勾）：

GPIOtimerfilenetwifi

然後三個關鍵選項：

  • branch 選 release（Lua 5.1）—— 5.3 吃更多 RAM
  • build type 選 integer —— 程式碼全面避開 %f，就是為了配合它
  • LFS size 從 0 改成 128KB —— 這一格是整件事的關鍵，漏了就得重編重燒

不要用 GitHub Releases 的預編譯版本：官方預編譯的 LFS size 是 0，這個專案用不了。TLS／sjson／SNTP／MQTT 一律不勾 —— 省下的 flash 才夠給 LFS。

2

把韌體燒進板子

用硬體檢查時確認過的序列埠，先清空再寫入：

$ esptool.py --port /dev/ttyUSB0 erase_flash
Erasing flash (this may take a while)...
Chip erase completed successfully in 8.7s

$ esptool.py --port /dev/ttyUSB0 --baud 115200 write_flash -fm dio 0x00000 nodemcu-release-integer.bin
Writing at 0x00080000... (100 %)
Hash of data verified.

-fm dio 是大多數 NodeMCU 開發板正確的 flash mode。燒完序列埠全是亂碼、找不到 > 提示字元，就換成 -fm qio 重燒。

接上序列埠（115200 baud）按一下 RST，橫幅裡有兩個數字要記下來：

NodeMCU custom build by frightanic.com
   branch: release
   commit: c8faff28          ← 打包 LFS 要用同一個 commit
   modules: file,gpio,net,node,tmr,wifi
 build type: integer
    LFS ver: 0x20000 bytes total capacity   ← 128 KB，對應 -m 131072
>
看到 > 提示字元、而且 LFS 容量不是 0，下層就位了。
LFS 顯示 none 或 0 → 回步驟 1，LFS size 那格忘了改，重編重燒。
3

建立 wifi_secret.lua（選配）

WiFi 帳密不寫在 wifi_cfg.lua 裡 —— 那個檔在版控裡，密碼進去就出不來了，pull 的時候也會跟本機設定打架。改成獨立一個檔，已經寫在 .gitignore：

$ cd firmware
$ cp wifi_secret.lua.example wifi_secret.lua
# 編輯它，填入：
return { ssid = "你的WiFi名稱", pass = "你的WiFi密碼" }

不建這個檔也可以 —— 找不到就走離線模式，沖洗邏輯照常運作，只是沒有網頁介面。所有連線判斷都是非阻塞的事件回呼，不會因為連不上而卡住狀態機。

4

打包 LFS 映像

打包工具 tools/luac.cross.int 已經在版控裡（commit c8faff28、integer build），clone 下來就能用。

它是 Linux ELF 執行檔，Windows 上跑不起來。在 cmd／PowerShell 打 luac.cross ... 只會得到「不是內部或外部命令」，補上完整路徑也一樣 —— 它必須在 Docker 容器裡執行。

在 repo 根目錄開 Git Bash：

$ MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W):/repo" \
    marcelstoer/nodemcu-build \
    bash -c "cd /tmp && cp /repo/firmware/cfg.lua /repo/firmware/log.lua \
      /repo/firmware/ro.lua /repo/firmware/web.lua /repo/firmware/wifi_cfg.lua . && \
      /repo/tools/luac.cross.int -f -m 131072 -o /repo/bin/lfs.img \
      cfg.lua log.lua ro.lua web.lua wifi_cfg.lua"
Image size: 33680
  • -m 131072 要對上步驟 2 橫幅印的 0x20000
  • 清單裡沒有 init.lua —— 它必須留在 SPIFFS，NodeMCU 開機是按檔名去那裡找的
  • 先 cp 到 /tmp 再編，是因為 luac.cross 拿檔名當模組名

產出的 lfs.img 是 gzip 壓縮的（開頭 1f 8b），所以檔案約 17 KB、比工具印的 Image size 小一半。這代表 用 grep 搜映像裡的字串一定搜不到 —— 那個現象跟「映像沒更新」長得一模一樣，很容易誤判。要驗就解壓再搜：

$ python -c "import gzip,sys; d=gzip.decompress(open('bin/lfs.img','rb').read()); \
    print('size',len(d),'hit',d.find(sys.argv[1].encode()))" '某段只有新版才有的字串'
size 34736 hit 11263          ← -1 就代表映像還是舊的
5

上傳三個檔案到 SPIFFS

lfs.img→ wifi_secret.lua→ init.lua

init.lua 一定最後傳：它是每次開機自動執行的入口，先上去而 LFS 還沒載入的話，開機就會找不到模組。

工具 A · nodemcu-tool

$ nodemcu-tool upload bin/lfs.img firmware/wifi_secret.lua
$ nodemcu-tool upload firmware/init.lua

這支工具需要 Node 12 —— 它依賴的 serialport 8 在新版 Node 上編不起來。

工具 B · ESPlorer

右上角選序列埠與 115200 baud、按 Open，左下「Open」選檔案後按「Save to ESP8266」，照上面的順序一個一個傳。

傳完一定要核對大小。ESPlorer 是逐行送的，序列埠一忙就會掉行 —— 而且不會報錯。曾經因此把 init.lua 截斷在第 79 行，開機直接噴 'then' expected near '<eof>'，看起來完全像程式碼寫錯。
> print(file.list()["init.lua"])
2379          ← 要跟本機檔案大小一模一樣，不一樣就重傳
6

把映像載進 LFS 區，再清掉 SPIFFS 舊副本

> node.LFS.reload("lfs.img")
裝置會自己重開機，把映像寫進 flash 的 LFS 區

這個 API 名稱在不同版本改過。先 print(node.LFS) 確認你這版有沒有 node.LFS；沒有的話用 node.flashreload("lfs.img")。

然後把 SPIFFS 裡的同名檔案清乾淨 —— 它們會蓋過 LFS 裡的模組，留著等於白開：

> file.remove("cfg.lc") file.remove("log.lc") file.remove("ro.lc")
> file.remove("web.lc") file.remove("wifi_cfg.lc")
.lua 原始碼如果還在也一併刪掉
這一步最容易漏。忘了刪的舊檔會靜默地蓋過 LFS 版本 —— 沒有任何錯誤訊息，只是你改的東西怎麼傳都不生效。
7

開機

按 RST。序列埠會依序看到：

[boot] relays forced off
... 5 秒安全視窗 ...
[mem] boot heap=4xxxx
[boot] LFS loader ok
[mem] ro   heap=4xxxx          ← 開了 LFS 應該接近 40000
[mem] web  heap=3xxxx
[wifi] 連線中 你的WiFi名稱
[wifi] 已連線 192.168.50.177
[web] 設定介面已啟動 :80
[mem] srv  heap=33048
四路繼電器第一件事就被放開成高阻抗（＝斷開）。模組是低電平觸發，GPIO 放手後由模組自己上拉到 5V，光耦完全截止。機器此時退化成單純的直通式 RO —— 這是刻意設計的開機安全狀態，不是故障。

懷疑剛上傳的東西有問題，就在那 5 秒內對序列埠打 stop() —— 取消這次啟動、不跑沖洗邏輯，也不必重燒韌體。

沒看到 [boot] LFS loader ok，代表映像沒載進去 —— 回步驟 6。
8

確認真的在跑

沒接 WiFi：留在序列埠看狀態訊息，或直接倒出事件記錄 —— 沒有網頁介面並不影響診斷能力：

> require("log").dump()

接了 WiFi、拿到 IP 之後：

$ curl http://192.168.50.177/status
state=IDLE pump=false safe=true used=false pending=false locked_ms=nil
due_ms=nil boot=7 flushes=0 aborts=0 flush_s=8 interval_m=30
isolate_ms=200 heap=31160

或用瀏覽器開 http://<裝置IP>/ 看狀態頁與參數表單。想手動測一次沖洗用 /flush（跳過補桶），要立刻停就開 /stop。

疑難排解

大多數狀況對得到三層其中一層。這張表裡的每一條都是實機上真的踩過的。

現象對到哪一層處理
開機後序列埠全是亂碼，找不到 > 韌體 · flash mode 不對 步驟 2 的 -fm dio 換成 -fm qio（或反過來），重新 erase_flash 再燒
module 'ro' not found，但 node.LFS.time 明明有值 LFS · loader 沒掛上 NodeMCU 3.0 的 package.loaders 沒有 LFS searcher，映像載入成功也一樣找不到模組。init.lua 裡的 package.loaders[3] 那段就是補這個，確認它有跑到
not enough memory / E:M 48 之類 LFS · 根本沒開，或被 SPIFFS 舊檔蓋掉 五個模組全載進 RAM 要 39.4 KB，而開機只有 41 KB —— 一定爆。檢查橫幅的 LFS 容量不是 0，且步驟 6 的 .lc／.lua 都刪乾淨了
'then' expected near '<eof>' 之類的語法錯 上傳 · 檔案被截斷 不是程式碼壞了。用 print(file.list()["init.lua"]) 對大小，不符就重傳
改了 Lua、也重打包上傳了，行為卻沒變 LFS · 映像其實是舊的，或被 SPIFFS 舊檔蓋掉 用步驟 4 的 gzip 解壓驗證確認映像內容；再確認步驟 6 的舊副本都清掉了。直接 grep 映像不算驗證，它是壓縮的
開機後一路重複重開機（boot loop） 上層 · 剛上傳的檔案寫壞 安全窗口內打 stop() 取消啟動，修好再重傳，不必重燒韌體
序列埠一直印「斷線 reason=...」，連不上自家 WiFi 路由器 · MAC 白名單分頻段 ESP8266 只有 2.4GHz。開了 Smart Connect 的路由器，白名單開關是全域的、清單卻是分頻段的 —— MAC 只加在 5G 清單裡，2.4G 清單是空的，結果就是全擋。把 MAC 加進 2.4G 白名單
WiFi 連上了，但 :80 沒起來、也沒有錯誤訊息 上層 · 事件註冊競態 wifi.sta.config 帶 auto=true，呼叫當下就開始連線；handler 註冊晚了就會漏接 GOT_IP，而那個事件不補發。wifi_cfg.lua 已改成先註冊再 config，並在 config 後補查一次 getip()
板子開機、繼電器先放開成斷開、沖洗狀態機在背景待命 —— 接下來就是量測水桶容積與泵流量，把 cfg.lua 裡 T_FLUSH_MAX_MS 這個硬上限，從保守的預設值調到實測後的安全值。細節見 docs/design-plan.md。
