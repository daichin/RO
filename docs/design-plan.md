# RO 純水回洗改造（直通式 1000G）

## Context

RO 系統是**直通式、1000 GPD、無產水儲存桶**。那顆小桶不是產水桶，是**專用的純水沖洗蓄水源**，改造後它永遠不進入飲用路徑。

原廠控制板的沖洗程序一律是「水泵工作＋進水閥開＋沖洗閥開」，只會用**自來水**正沖，停機後膜殼裡留下的是自來水。

**目標**：追加一段用小桶純水做的正沖，讓膜在靜置時泡在純水裡。減少結垢、避免長菌、降低第一杯水的 TDS。

> **什麼是純水正沖**：純水從**膜的進水口**進去，沿著膜面橫掃，由**濃水口**排到排水管。走向跟正常製水完全相同，差別只在推進去的是純水而不是自來水。目的是把膜殼裡殘留的水換掉 —— 原廠停機時留在裡面的是自來水，換成純水後既沒有結垢離子也沒有養分。

### 已確立的系統事實

- 高壓開關是**常閉型需求開關**（達壓斷開）：龍頭開 → 管路洩壓 → 閉合 → 製水；龍頭關 → 充壓 → 斷開 → 停機。
- 曾測到「開機後 15 秒才出水」是**空桶在吸水**，不是啟動延遲。管路平時是滿的，只要桶被隔離，造出來的水直接從龍頭出去，沒有等待。
- 只靠桶可出水 30 秒。
- **B = 10 × A**（B = 膜殼容水量，A = 高壓開關死區水量），高壓開關無法調整。
- 廢水閥是**一體式**：不通電走內建限流孔，通電全開。
- 純水回泵線已就位：桶 → 電磁閥 → 逆止閥 → 泵前三通。
- 隔膜泵停機時不通水 → 沖洗必須讓泵運轉。
- 控制板：輸出 進水閥 ×1、廢水閥 ×2、水泵（經低開繼電器 → XT60）；輸入 高壓開關、低壓開關；5V 漏水繼電器串在低壓訊號鏈上。
- 控制板的 8 秒自來水沖洗條件是「**累計製水超過 60s**」，不是每次退出製水都跑。

---

## 核心設計：用一顆隔離閥讓沖洗對控制板隱形

在**十字接頭 → 壓力桶**之間加一顆常閉電磁閥 **K_tank**，並把**沖洗取水的三通移到 K_tank 的桶側**。

高壓開關留在管路側。K_tank 一關，沖洗只動到桶，管路側完全不受擾動：

- 沖洗時廢水閥全開，膜的進水側幾乎沒有背壓，跨膜壓差趨近於零，**透水量可以忽略**。
- 而且純水管上那顆逆止閥的另一側是充飽壓力的管路，膜的純水側**根本推不開它**。
- 所以整個沖洗期間沒有任何水進入管路側 —— 壓力不變、**高壓開關一路保持斷開、板子完全不知道發生過沖洗**。

**沖洗結束的瞬間就已經是目標待機狀態**：膜殼裡是純水，管路有壓，板子在睡。

藍色高壓開關那條線**完全不碰**。

## 循環

| 階段 | K_tank | 板子 | 膜殼內 |
|---|---|---|---|
| **待機** | 關（斷電）| 睡 | **純水** ✓ |
| 開龍頭 | 關 | 製水，**水直接給龍頭** | 自來水 |
| 關龍頭 | 關 | 管路充壓 → 停機 | 自來水 |
| 補桶 | **開** | 製水填桶 → 停機 | 自來水 |
| 純水沖洗 | **關** | 睡（毫不知情）| → **純水** ✓ |

**補桶必須排在沖洗之前** —— 反過來的話補桶會把自來水推回膜殼，前功盡棄。

桶只在補桶時進水、在沖洗時出水，**永遠不供應龍頭**。

## 水路變更（只有兩處）

1. 在**十字接頭 → 壓力桶**那一段裝上 K_tank。
2. 把**沖洗取水的三通**從十字接頭移到 **K_tank 的桶側**。

> **前提**：高壓開關必須位於十字接頭的**上游**（水路圖順序是 `膜純水口 → 逆止閥 → 高壓開關 → 十字`）。**動工前目視確認實機順序** —— 若開關實際在桶那一側，整個方案的前提不成立。

另外確認：純水回泵線的逆止閥方向是「桶 → 泵前」；純水電磁閥是**常閉（NC）**型；桶球閥全開、2 分管無壓折。

## 電路

線色：`12粉=24V+`、`11白=24V−`、`4/10紅=沖洗閥`、`6/9黑=進水閥`、`5/8綠=水泵±`、`1/7黃=低壓開關`、`2/3藍=高壓開關`、`橘=水泵−`、`藍綠=低壓·漏水鏈`。

**完全不碰藍色高壓開關那條線。**

### 輸出（4 路）

| 繼電器 | 接法 | 說明 |
|---|---|---|
| **K_perm** | `24V+ → 接點 → 純水閥 → 24V−` | 全新迴路，與控制板零互動 |
| **K_waste** | **單刀**，串在紅色 `4` 上：`NC` ← 控制板的 `4`，`NO` ← 自己的 `24V+`，`COM` → 廢水閥線圈正極 | 實測：`10` 永遠 0V、只有 `4` 會跳 +24V ⇒ 控制板用**高側開關**，`10` 就是接地。廢水閥負極本來就固定在地，**只需接管正極** |
| **K_pump** | 接點**並聯**在「低開繼電器 → XT60 → 水泵」那段 24V 供電接點上 | 不碰控制板電子線路 |
| **K_tank** | `24V+ → 接點 → K_tank 閥 → 24V−` | 常閉閥：待機斷電＝桶隔離（省電） |

> **失效方向**：全部斷電＝全部復歸。K_tank 關 → 桶永久隔離 → 機器退化成一台單純的直通式 RO，照常出水，只是不再沖洗。**這是可接受且安全的失效模式。**

### 輸入（2 路）

| 訊號 | 取樣點 | 判讀 |
|---|---|---|
| **IN1 泵狀態** | 控制板**橘色 `水泵−`** 線（低側輸出） | **低電位 = 泵運轉**（反相）。下降沿＝板子啟動；**上升沿＝板子停機**（本設計的主要事件） |
| **IN2 低壓·漏水鏈** | 藍綠色那條 | 低 = 缺水或漏水 → **立即 ABORT** |

兩路都用 `100kΩ + 12kΩ` 分壓對地（24V → 約 2.6V），取樣電流約 0.2mA，負載可忽略。

> **不加任何額外的保護元件。** 那顆 100kΩ 本身就是保護元件。
>
> IN1 直接掛在控制板橘線上，控制板切斷低側時低開繼電器線圈的反電動勢會把該節點頂高。但**算一下就知道不用擔心**：假設上游只有電晶體的雪崩箝位、橘線衝到 60V —— 分壓中點想升到 6.4V，但 ESP8266 內部箝位二極體會壓在約 3.9V，此時流過 100kΩ 的是 (60−3.9)/100k ≈ 0.56 mA，扣掉經 12kΩ 到地的 0.33 mA，真正灌進 ESP 內部保護的只有 **約 0.24 mA**。
>
> 即使完全沒有上游箝位、衝到 300V，也只有約 2.6 mA，而且是微秒級暫態 —— ESP 的內部保護結構吃得下。
>
> **低開繼電器已經穩定運作很久，不去動它的線圈。** 為了一個算出來不成立的風險去改一台正常的機器，代價大於效益。
>
> 繼電器模組那四路輸出本來就有光耦隔離、線圈上也有內建續流二極體，同樣不用加東西。

### 繼電器模組必須設成低電平觸發，並用 open-drain 驅動

模組規格（5V 版）：**觸發電壓 低 = 0–1.5V，高 = 3.8–5V**。

ESP8266 的 GPIO 只有 3.3V，**落在 1.5V 與 3.8V 中間，兩邊都不到** —— 高電平觸發根本不在規格內，不是餘裕問題。

板上的 `S1`–`S8` 跳線可選觸發極性：**`com`–`low` 短接 = 低電平觸發**。設成低電平後 0V 觸發、3.3V 不觸發，完全在規格內。

**再用 open-drain 讓「關」也變成零殘流**：低電平觸發配 5V 供電時，GPIO 拉高到 3.3V，LED 兩端還剩約 0.5 mA 殘流。改成「關 = 放開成高阻抗」，由模組自己上拉到 5V，LED 完全截止。

```lua
gpio.mode(pin, gpio.OPENDRAIN)
gpio.write(pin, gpio.LOW)   -- 繼電器開
gpio.write(pin, gpio.HIGH)  -- 放開 → 5V → 繼電器關
```

（韌體若無 `OPENDRAIN`，用 `gpio.mode(pin, gpio.INPUT)` 當關、`gpio.OUTPUT` + 寫 LOW 當開。）

**開機狀態天然安全**：ESP8266 開機時 GPIO 預設是輸入（高阻抗），在低電平觸發下等同「放開」→ 模組上拉到 5V → 四路斷開。上電、重開機、燒錄韌體全程都是如此。

`ro.lua` 的常數要對調：`local ON, OFF = gpio.LOW, gpio.HIGH`。

> 只用 6 個 I/O，還有餘裕 —— 不必為了腳位換 ESP32。

## 控制邏輯

**觸發是計時器，不是用水事件。** 沖洗完成後開始計時；`MIN_INTERVAL` 內用水一律不沖；時間一到就補桶＋沖洗，若那一刻正在用水，就等這次用完立刻做。

> **為什麼不用「用水後才判斷間隔」**：那樣一旦某次用水剛好落在鎖定窗內就會被跳過，而如果之後很久沒人用水，膜殼就一直泡在自來水裡。例：09:55 沖洗、10:00 用水（跳過）、18:00 才再用水 → 膜泡了 8 小時自來水。改成計時器後，**任何一次用水之後 30 分鐘內，膜一定會被換回純水**。

**`used` 旗標**：計時器到期時，只有「上次沖洗之後板子有製過水」才會真的去沖。完全沒人用水的話，膜殼裡本來就是純水，再沖一次只是拿純水換純水 —— 純粹的空轉（一天 48 輪、約 14 L 純水排掉、96 次額外泵啟停）。加了這個旗標，長期外出時完全不耗水，而「用水後 30 分鐘內必回純水」的保證絲毫不變。

> 旗標**只在 IDLE 狀態下**由 IN1 下降沿設定。REFILL 階段板子當然也在製水，但那是我們自己叫的、而且緊接著就沖洗，不能拿來自我觸發。

```
IDLE    K_tank 關；膜殼裡是純水
 ├─ IN1 下降沿（板子開始製水 = 有人用水）→ used = true
 │
 └─ used 且 計時器到期（now − last_flush >= MIN_INTERVAL）
      ├─ 板子正在製水（IN1 低）→ 標記 pending，等這次用完
      └─ 板子已停機（IN1 高）→ REFILL

        pending 期間，IN1 上升沿 → REFILL

REFILL  K_tank ON → 桶接回管路 → 壓力被拉低 → 板子自行製水填桶
 └─ IN1 上升沿（板子停機 = 桶已充飽）→ FLUSH

FLUSH
 1. K_tank OFF ← 桶與管路隔離，之後的動作板子完全看不到
 2. 等 T_ISOLATE ← 先讓 K_tank 確實關到底，才動其他閥（見下）
 3. K_waste ON（全開）、K_perm ON
 4. 等 T_PRIME 充管（避免泵空打）
 5. K_pump ON，運轉 T_FLUSH
 6. K_pump OFF
 7. 等 2s → K_perm OFF
 8. 等 2s → K_waste OFF（濃水回到限流狀態）
 9. 記錄 last_flush、used = false → IDLE

 中止條件：
 ├─ IN2 異常    → ABORT
 └─ IN1 下降沿  → ABORT（見下方「沖洗撞上用水」）

ABORT   四路繼電器全部復歸 → IDLE
```

**為什麼 K_tank 要先關、隔一段再開其他閥（`T_ISOLATE`）**

穩態下 K_waste 與 K_perm 都不會影響管路端，有兩道隔離：K_perm 接的是 K_tank **桶側**的三通（而且那條線上還有桶 → 泵前的逆止閥）；K_waste 開的是**濃水側**，而管路端與膜的純水側之間有逆止閥（膜 → 管路單向），管路的水推不回膜裡。

風險在**切換瞬間**。繼電器與電磁閥不是同時動作的。若 K_tank 還沒關到底、K_perm 就已經開了，那一瞬間**桶和管路同時通到泵前三通**，水往低壓的泵前流，管路壓力被拉掉 —— 掉夠多就跳高壓開關，板子醒來，「隱形」的前提當場破功。

機率不高（K_tank 是常閉閥，關閉靠彈簧釋放，通常比 K_perm 的線圈吸合快），但**不保證** —— 閥老化、彈簧變弱、接點時間差都可能讓順序反過來。消除這個窗口的成本是零。

典型繼電器動作 5–15 ms、電磁閥 10–30 ms，100 ms 就夠；取 **200 ms** 是給老化留餘裕。tick 是 100 ms，所以就是 2 個 tick，實作成一個 `ISOLATE` 狀態。

K_waste 與 K_perm 之間**不用**再錯開 —— 一個在濃水側、一個在桶側，互不干涉。

**沖洗撞上用水**：沖洗期間 K_tank 是關的，板子應該完全不動。若此時 IN1 轉低，代表使用者開了龍頭把管路壓力放掉了。這時**立刻中止沖洗、把機器讓回去** —— 因為沖洗中廢水閥全開，膜建不起壓力，硬撐下去使用者會沒水喝。

中止時**不更新 `last_flush`、也不清掉 `used`**，回到 IDLE 後條件重新成立（計時器仍過期、`used` 仍為真），而板子此刻正在製水，於是自動進入 pending，等這次用水結束就重試。不需要額外的重試邏輯。

> 這個中止條件同時是核心假設的哨兵：如果在**沒有人用水**的情況下也觸發，就代表「沖洗對板子隱形」的隔離假設不成立，日誌會直接告訴你。

全程不需要對時，也不需要 RTC —— 計時用開機以來的毫秒累加。

### 參數（可執行時變更）

| 參數 | 預設 | 硬上限 | 說明 |
|---|---|---|---|
| `T_FLUSH` | **8s** | **15s** | 沖洗時間。上限是保護，見風險 1 |
| `MIN_INTERVAL` | **30 分鐘** | — | 沖洗週期。時間一到就補桶＋沖洗；期間用水一律不沖 |
| `T_ISOLATE` | 200ms | — | K_tank 關閉後、開其他閥之前的間隔。消除切換瞬間的重疊窗口 |
| `T_PRIME` | 2s | — | 充管延遲，避免泵空打 |

**設定介面**：NodeMCU 起一個極小的 HTTP 服務，可讀取／修改 `T_FLUSH` 與 `MIN_INTERVAL`，數值寫進 flash，開機載入。另提供一個手動觸發端點方便測試。

- **韌體必須拒絕超過硬上限的設定值**。桶在沖洗時是封閉容器、沒有補水，打錯一個數字就是泵乾轉。
- 設定介面與 WiFi **不得阻塞狀態機或 ABORT 路徑**：連線失敗、重連、OTA 都要能在背景失敗而不影響沖洗時序。斷網時必須照常用最後存下的參數運作。

## 動工前的量測

### 一 · 桶的實際可用容積

從龍頭放到沒水，用量杯接，記錄體積。

### 二 · B（膜殼容水量）

把兩支膜的進出管拆下，把膜殼裡的水倒進量杯。

### 三 · 泵在沖洗狀態下的流量

手動給廢水閥與純水閥通電、跑泵，用量杯接排水管量固定秒數的排水量。

**這三個數字決定 `T_FLUSH` 的可行範圍**：`T_FLUSH × 泵流量` 必須**明顯小於桶可用容積**（建議不超過 60%），同時盡量接近 B 才有好的置換率。若 B 逼近桶容積，餘裕很薄，就只能做部分置換 —— 沖洗不是全有全無，置換一半仍是實質改善。

## 風險與陷阱

1. **泵乾轉（最需要注意）**：K_tank 關閉時桶是封閉、無補水的容器。1000G 系統的泵流量大（約 3–4 L/min），若桶只有 0.8 L 左右，**十幾秒就能抽乾**。`T_FLUSH` 的硬上限就是為此存在，量測三做完後應該把它調到實測值的安全範圍內。
2. **K_pump 繞過漏水保護**：並聯在泵供電上，繞過了「漏水繼電器 → 低壓開關」的保護鏈。優先查漏水繼電器有沒有第二組備用接點可串聯；沒有的話靠 IN2 做 ABORT，且該檢查必須在主迴圈最前面、**不得被 WiFi／HTTP／OTA 等阻塞呼叫擋住**。
3. **高壓開關的實際位置**：整個方案假設它在十字接頭上游。動工前目視確認。
4. **K_waste 串在 `4` 上，不要並聯**。實測 `10` 永遠 0V、`4` 才是高側輸出，所以單刀就夠；但要**串接**（`NC` 走控制板、`NO` 走自己的 24V+），不要用並聯的方式把 24V+ 灌到控制板的輸出腳上。
5. **沖洗撞上用水**：沖洗只有十幾秒，但期間廢水閥全開、膜建不起壓力，若使用者剛好開龍頭會沒水喝。靠 IN1 下降沿中止並讓回機器（見控制邏輯）。中止不更新 `last_flush`，用完水會自動重試。
6. **REFILL 卡住**：若因故板子一直不停機（例如缺水），狀態機會卡在 REFILL。需要一個逾時（建議 10 分鐘）退回 IDLE 並把 K_tank 關回去。
7. **開機瞬間繼電器誤動作**：低電平觸發 + open-drain 讓高阻抗即等於「關」，開機時天然安全。仍須實機驗證上電、重開機、燒錄期間四路都不動作。
8. **不加任何保護元件，也不去動低開繼電器的線圈**。分壓的 100kΩ 本身就把故障電流限在 0.24 mA 等級（算式見輸入段），而那顆繼電器已經穩定運作很久。繼電器模組的四路輸出有光耦隔離、線圈也有內建續流二極體。**整套改造不新增任何一顆二極體。**

## 驗證

**一 · 乾式**（不通水、泵的 XT60 拔掉）
0. **先確認跳線與觸發極性**：`S1`–`S4` 設成 `com`–`low`。接一路，用 Lua 來回切十次，確認吸合與釋放都乾脆、放開時沒有嗡嗡聲。**這是唯一能證明 3.3V 驅動與殘流沒問題的方法**，先過這關再往下做。
1. 四路輸出接 LED 或萬用電表。反覆上電、重開機、燒錄韌體，確認**全程不動作**。
2. 手動觸發一次流程，碼錶核對時序。
3. 透過 HTTP 改 `T_FLUSH`，重開機確認值有存活；再送一個超過硬上限的值，確認被拒絕。

**二 · 訊號**（通水、泵仍斷開）
4. 確認橘線分壓中點在 0V／2.6V 之間乾淨切換。**因為沒有加任何保護元件，這項改用實測來確認判斷正確** —— 有示波器就看有沒有超過 3.3V 的尖峰；沒有的話，長跑期間留意 IN1 讀值是否一直正確（GPIO 被打壞通常表現為讀值卡在某一側不再變化）。
5. 正常用水一次，確認 IN1 的上升沿被抓到、且對應到板子確實停機。
6. 關進水球閥模擬缺水，確認 IN2 變低、狀態機拒絕觸發。
7. 沖洗中人為讓 IN2 變低，確認 ABORT 在 1 秒內把四路全部復歸。

**三 · 濕式**
8. 手動觸發一次完整流程。量杯接排水管記錄排水量，與量測三對照，據此定案 `T_FLUSH` 與硬上限。
9. 聽泵聲，確認沒有空打的乾轉異音；**特別注意沖洗末段**，那是桶最接近見底的時刻。
10. **關鍵驗證**：沖洗全程用萬用電表盯著橘線 —— 板子**不可以**有任何動作。這是「沖洗對板子隱形」這個核心假設的直接驗證。
10b. **`T_ISOLATE` 有沒有效**：把它暫時設成 0 再跑幾次沖洗，看板子會不會在起始瞬間被吵醒。若設 0 就會醒、設 200ms 不會醒，就證明這個延遲確實在擋住切換窗口；若兩者都不會醒，代表 K_tank 的釋放本來就夠快，但保留這個延遲當保險。

**四 · 循環與失效安全**
11. **完整循環**：正常用一次水 → 確認 30 分鐘內再用水**不會**觸發沖洗 → 什麼都不做等到 30 分鐘，確認**自己**就開始跑補桶與沖洗（不需要再用一次水）。
11b. **pending 路徑**：把 `MIN_INTERVAL` 暫時改成 2 分鐘，在計時器到期的那一刻持續開著龍頭，確認系統等到你關龍頭才開始補桶。
11c. **撞上用水的中止**：沖洗跑到一半時開龍頭，確認四路立刻復歸、你馬上有水喝，而且用完水後系統會自動重試。
11d. **`used` 旗標**：沖洗完成後**完全不碰龍頭**，確認過了 30 分鐘、60 分鐘都不會有任何動作。這是長期外出時不空轉的驗證。
12. 開龍頭確認**沒有出水延遲**（驗證 K_tank 關閉時造水直接供龍頭）。
13. **失效安全**：待機中直接拔掉 NodeMCU 電源，確認四路釋放、機器退化成單純直通式 RO 且照常出水。

**五 · 長跑**
14. 連續觀察一週，記錄每日沖洗次數與桶的補水表現。
15. 效果驗證：改造前後各量一次「靜置數小時後第一杯水的 TDS」，用這個數字回頭校正 `T_FLUSH`。

# 事件 log（追加功能）

## Context

現在裝置**不保存任何歷史**：只有累計次數和「最後一次」中止原因，重開機全部歸零。

這讓驗證階段五（連續觀察一週）沒東西可看，但更嚴重的是**哨兵條件失效**。沖洗中偵測到控制板啟動就中止，這是「沖洗對板子隱形」這個核心假設的直接驗證 —— 可是憑 `aborts=3` 分不出來是「你自己開龍頭撞到三次」還是「凌晨三點自己跳了三次」。**後者代表整套設計的前提不成立**，而那正是最需要知道的事。

Flash 有約 3 MB，RAM 只有約 40 KB —— 差 75 倍。所以 log 寫**檔案**，不是 RAM 環形緩衝區。順帶解決重開機不丟資料。

## 時間戳：由訪客校時，不加模組

裝置沒有 RTC，也刻意沒裝 `sntp`（狀態機不需要對時）。改成：

- 網頁載入時用三行 JS 呼叫 `/settime?t=<epoch>&tz=<分鐘偏移>`，裝置記下 `epoch_at_boot` 與時區
- 輪詢腳本也可以順便帶上，所以就算不開網頁也會校到
- **每一行 log 在寫入時就把當下的 epoch 一起寫進去**（校時前寫的那些留 `-`）

這樣讀取時不需要回頭找錨點、不需要兩趟掃描，`curl` 直接看也是可讀的時間。**不新增任何 NodeMCU 模組。**

## 順帶要修的一個真實缺陷：中止迴圈

現在中止不更新 `last_flush` 也不清 `used`，所以會自動重試 —— 這在「使用者開龍頭」的情境下是對的。

但如果中止的原因是**隔離假設不成立**（沖洗本身吵醒了板子），就會變成：補桶 → 沖洗 → 板子醒 → 中止 → 板子停 → 補桶 → … **緊迴圈**。會一直操泵，也會把 log 寫爆。

加上**連續中止退避**：連續 3 次中止而中間沒有一次成功沖洗，就進入長鎖定（6 小時）並記一筆顯眼的 log。成功沖洗或手動觸發時清零。

## 檔案

| 檔案 | 變更 |
|---|---|
| `firmware/log.lua` | **新增**。事件寫入、輪替、epoch → 本地時間換算 |
| `firmware/ro.lua` | `enter()`／`abort()` 呼叫 log；連續中止退避；`boot_id` |
| `firmware/web.lua` | `/settime`、`/log`（**串流**）、首頁加連結與校時 JS |
| `firmware/README.md` | log 格式與端點說明 |

## log.lua

**行格式**（純文字，一行一筆，好 grep）：

```
<boot>.<uptime_s> <epoch|-> <KIND> <state> <text>
```

```
7.1234 1757001234 STATE REFILL 週期到，開始補桶
7.1250 1757001250 STATE IDLE 沖洗完成，膜殼裡是純水
7.1801 1757001801 ABORT PRIME 使用者開了龍頭，把機器讓回去
3.90 - BOOT IDLE 已啟動（校時前）
```

**KIND**：`BOOT`／`STATE`／`ABORT`／`CFG`（有人改參數）／`TIME`（校時）／`LOCK`（連續中止退避）

**開機序號**：存在 `boot.txt`，每次啟動遞增。沒有 RTC 時它是唯一能區分不同開機階段的東西。

**輪替**：`log.txt` 超過 **128 KB** 就改名成 `log.1.txt`（覆蓋舊的），重開新檔。上限 256 KB，對 3 MB 的 SPIFFS 微不足道。以實際約每天 100 行、每行約 60 bytes 估算，兩個檔約可留 **40 天**。

**寫入方式**：每次事件 open → append → close。不跨事件持有 handle，重開機不會留下半開的檔案。

**epoch → 本地時間**：在 Lua 裡做日曆換算（約 20 行），配合 `/settime` 帶進來的時區偏移。這樣 `curl` 或手機瀏覽器看到的都是 `2026-09-04 03:12:45`，不是一串數字。

## 兩個實作上的硬限制

**1. `/log` 必須串流，不能組字串**

`web.lua` 現在是把整個回應組成一個 Lua 字串再 `sck:send()`。log 檔可達 128 KB，而自由堆積只有約 40 KB —— **直接讀進來會當機**。

`/log` 要走獨立路徑：`f:seek()` 定位後，每次讀 512 bytes、`send()`、在 `on("sent")` 回呼裡讀下一塊，串完才 `close()`。

預設只回**最後 16 KB**（`f:seek("end")` 取檔案大小再倒推），`?full=1` 才從頭串完整檔案並接著串 `log.1.txt`。

**2. 寫檔會卡住 100ms tick**

SPIFFS 寫入要幾到幾十毫秒，而 log 是在 tick 回呼裡觸發的。事件很稀疏（每個循環約 6 筆），沖洗時序也有餘裕，可以接受。

但**中止路徑的順序不能動**：`M.abort()` 現在第一行就是 `all_off()`，安全動作先完成、之後才記 log。這個順序必須維持。

## 端點

| 路徑 | 作用 |
|---|---|
| `/log` | 最後 16 KB，`text/plain`，串流 |
| `/log?full=1` | 完整（含輪替檔） |
| `/log?clear=1` | 清空 |
| `/settime?t=<epoch>&tz=<分鐘>` | 校時。首頁 JS 自動呼叫一次 |

首頁加一個「查看 log」連結，以及：

```html
<script>fetch('/settime?t='+Math.floor(Date.now()/1000)
  +'&tz='+(-new Date().getTimezoneOffset()))</script>
```

## 驗證

1. **日曆換算先在 PC 上驗**。沒有 Lua 工具鏈，所以把同一套演算法照抄成 Python，對幾百個隨機 epoch 與多個時區偏移跟 `datetime` 交叉比對。**這是最容易寫錯又最不容易在裝置上發現的部分**，一定要先驗過再燒。
2. **串流不爆記憶體**：讓 log 長到 100 KB 以上（可用 `/log` 前先灌假資料），然後 `curl` 抓完整檔案，同時盯 `node.heap()`。抓完後堆積要回到原本水位，不能持續下降。
3. **輪替**：把上限暫時改小（例如 2 KB）跑一陣子，確認 `log.txt` 會變成 `log.1.txt`、新檔重開，且 `?full=1` 兩個檔都讀得到。
4. **校時**：重開機後先 `curl /log`，確認新行的 epoch 欄位是 `-`；用瀏覽器開一次首頁，再 `curl /log`，確認之後的行有正確的本地時間。
5. **中止退避**：手動連續觸發三次會中止的情況（例如沖洗中一直開著龍頭），確認第三次之後進入鎖定、log 有 `LOCK` 一筆，且成功沖洗一次後計數歸零。
6. **不影響時序**：開著序列埠跑一次完整循環，用碼錶核對沖洗各階段秒數與加 log 之前一致（寫檔不應造成可見延遲）。
