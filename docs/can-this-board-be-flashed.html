Hardware check · before flashing

Can this NodeMCU actually be flashed?

Before you put the RO permeate-flush firmware on the board, confirm the board will talk back at all. Nine checks, in order, using the USB port and esptool — no firmware upload yet.

ESP8266 · NodeMCU devkit Windows / macOS / Linux ~10 min

Before you start

  • The NodeMCU board itselfLook near the USB port for a small chip labelled CH340, CH9102F, or CP2102 — that's the USB-to-serial bridge, and it decides which driver you need next.
  • A data USB cable, not a charge-only oneMany micro-USB / USB-C cables only wire the power pins. If the board's LED lights up but your computer never lists a new port, this is the first thing to swap.
  • A computer with a terminal and Python 3For installing and running esptool, the same tool the Arduino IDE and NodeMCU flashers use underneath.

The nine checks

Work top to bottom. Each check either passes or points straight at the next thing to fix — you don't need to understand everything before proceeding.

1

Identify the USB-serial chip

Flip the board over or look next to the USB connector. The small IC there is almost always one of three: CH340G, CH9102F, or CP2102/CP2102N. This alone tells you which driver to look for on step 3.

No visible marking, or it's sanded off? Assume CH340 — it's the chip on the vast majority of NodeMCU clones.

2

Plug in with a known-good data cable

Connect the board directly to your computer (skip hubs and charge-only extension cables for this test). The onboard LED should light immediately — that only confirms power, not data.

Cable is suspect if the LED lights but nothing shows up in steps 4–5. Try a different cable before touching any driver or software.
3

Install the USB-serial driver

macOS and Linux usually have CH340 and CP2102 support built into the kernel already. Windows almost always needs a driver installed manually, matched to the chip from step 1:

  • CH340 / CH9102F → WCH's driver (search "CH341SER" or "CH9102" driver from WCH-IC)
  • CP2102 / CP2102N → Silicon Labs' "CP210x USB to UART" driver

Linux only: add yourself to the serial-port group so you don't need sudo for every command — sudo usermod -a -G dialout $USER, then log out and back in.

4

Confirm the OS sees a new serial port

With the board plugged in, check for a new port:

# Windows — Device Manager
Ports (COM & LPT)
  > USB-SERIAL CH340 (COM5)      ← note this COM number

# macOS
$ ls /dev/cu.*
/dev/cu.wchusbserial14110         ← or SLAB_USBtoUART

# Linux
$ dmesg | tail
[  102.4] ch341 1-1:1.0: ch341-uart converter now attached to ttyUSB0
$ ls /dev/ttyUSB*
/dev/ttyUSB0
Pass: a port appears. Write down its name — you'll pass it to every command below.
Fail: nothing new appears → back to step 2 (cable) or step 3 (driver).
5

Install esptool

$ pip install esptool
$ esptool.py version
esptool.py v4.7.0

If esptool.py isn't found on your PATH, use python -m esptool version instead — same tool.

6

Ask the chip who it is

This is the real test. Replace the port with the one from step 4:

$ esptool.py --port /dev/ttyUSB0 chip_id
esptool.py v4.7.0
Serial port /dev/ttyUSB0
Connecting....
Detecting chip type... ESP8266
Chip is ESP8266EX
Features: WiFi
Chip ID: 0x00a1b2c3
Uploading stub...
Running stub...
Stub running...
Chip ID: 0x00a1b2c3
Hard resetting via RTS pin...
This is the pass condition. If you see Detecting chip type... ESP8266 followed by a Chip ID, the board is alive, the bootloader responds, and it can be flashed.
7

If it timed out: try manual bootloader entry

NodeMCU boards normally auto-reset into the bootloader using the CH340/CP2102's DTR/RTS lines wired to GPIO0 and RST. When that circuit doesn't cooperate:

  1. Hold the FLASH button (GPIO0) down
  2. Tap and release RST while still holding FLASH
  3. Release FLASH
  4. Re-run the chip_id command from step 6 within a few seconds
8

Read the flash size & confirm write access

Chip ID alone proves the board talks. This proves it can be written to:

$ esptool.py --port /dev/ttyUSB0 flash_id
Manufacturer: c8
Device: 4016
Detected flash size: 4MB

Most NodeMCU boards report 4MB. A mismatch or garbled output here usually means a flaky connection, not a dead board — retry once before assuming the worst.

9

Back up the current flash contents

Optional, but cheap insurance before this board gets the permeate-flush firmware — a full dump you can restore from if anything goes wrong later:

$ esptool.py --port /dev/ttyUSB0 read_flash 0x0 0x400000 backup_before_ro_flash.bin

Troubleshooting

Symptoms map to one of five causes almost every time.

SymptomLikely causeFix
No port appears at all Charge-only cable, or driver not installed Swap the cable first — it's the more common cause — then reinstall the driver for the chip from step 1
Permission denied opening the port Your user isn't in the serial device group (Linux) sudo usermod -a -G dialout $USER, then log out/in
Failed to connect... Timed out waiting for packet header Auto-reset circuit didn't trip, or a bad cable Manual bootloader entry (step 7); try a shorter/known-good cable
Board resets or browns out mid-command USB port can't supply enough current Use a rear/motherboard USB port or a powered hub instead of a laptop's front USB or a hub with other devices drawing current
Garbled text on serial monitor, not on esptool Wrong baud rate for the monitor (esptool itself auto-negotiates) NodeMCU firmware's console defaults to 115200; the ROM bootloader briefly prints at 74880 right after reset — both are normal
Board confirmed flashable? The next step is flashing the NodeMCU (Lua) firmware image itself, then getting this project's Lua onto it — covered in docs/from-blank-board-to-running.html and firmware/README.md.
